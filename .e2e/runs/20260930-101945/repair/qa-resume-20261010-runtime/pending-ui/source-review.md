## Process split

`controller.py` is local and reads the existing mode-0600 repair connection. It uses that private token only for fresh read-only Hub checks and to create/run/delete the parent helper Task. The embedded parent command contains reviewed Python source, the watchdog source, owner fingerprints, and QA IDs; it does not contain the connection file contents, a bearer, or browser credentials.

The local controller creates a unique retry-0, no-schedule Command Task targeting only Native-4 parent `03cb50cc-eab6-4afd-bbe0-f73c4e326773`. Because Task creation advances GlobalRev, it waits for the four original Native Nodes and the owned child to return online/synced, then repeats the API identity, exact child Task, child schedule, and PENDING/RUNNING guards immediately before the helper Run. API guards record revisions by timestamp and do not compare unrelated reads from different times.

`arm_control.py` runs on the Native-4 parent and has no API client, private connection path, token, or auth header. It checks the exact parent Unit/MainPID read-only, exact child/proxy PID/startticks/UID/executable SHA/argv/cgroup, owned root/manifest/config/DB fingerprints, and opens only the owned child SQLite DB in `mode=ro`. The DB queries use fields already present in `attempt02/child-runtime-readonly-evidence.json`: `identity`, `sync_state.global_revision`, `tasks(id,definition_json,revision,enabled)`, `schedules(id,definition_json,revision,enabled)`, and `executions(id,task_id,node_id,status,...)`. It requires valid identity, `quick_check=ok`, exactly the owned child Task, zero schedules, and no child PENDING/RUNNING execution.

## Watchdog ordering and release

The parent helper creates a unique 0600 lock file inside the child-owned root and holds `flock(LOCK_EX)` before starting `watchdog.py` as UID/GID 65534 in a detached session. The watchdog verifies the exact root/manifest/controls owner, creates a nonce/task-bound READY file, then blocks on that same lock. The parent requires READY to report the exact watchdog PID, nonce, and TaskID while the process remains alive, and repeats its live process, Unit, DB, config-SHA, root, and control-content guards immediately before the write.

The controller treats `.e2e/test-data.json` `repair_environment_state.backend_child_20261008.latest_owner_guard.owner_manifest_sha256` as the current recorded manifest fingerprint and verifies it matches the linked latest restart evidence's `result.owner_manifest_sha256_after` before creating a parent helper Task. This prevents an old `db-fault/attempt02/child-runtime-readonly-evidence.json` pre-restart fingerprint from overriding the newer Native4 restart owner record. It remains only a recorded expected value; the remote helper still performs a fresh exact manifest SHA guard before any watchdog/control action.

The Native4 owner-manifest v1 schema is `owner_marker`, not `owner_nonce`. The arm helper and watchdog now verify `node_id`, `agent_id`, `directory_dev`, `directory_ino`, and `directory_uid`; they also require the exact owned-root `owner.marker` path to be a regular file owned by the expected UID and to match the manifest's nonempty `owner_marker` string byte-for-text. The marker value is never logged or persisted as evidence. Both helpers retain the pinned manifest SHA check, root inode/UID, config, process, cgroup, Unit, and DB guards.

While still holding the lock, the parent writes only `hold_types:[RUN_EXECUTION]` plus the unique `qa_hold_nonce`/`qa_hold_task_id`, then writes the monotonic deadline state at `arm + 8s` and unlocks. The watchdog cannot expire before this handshake. If the parent exits before writing a valid deadline, the watchdog clears only a matching owned hold immediately; if it exits after the deadline state, the watchdog waits to that absolute monotonic deadline. A second arm cannot reuse the O_EXCL nonce lock. On release, the watchdog rechecks the exact nonce and TaskID, removes only its `RUN_EXECUTION` entry and its two marker keys, preserves any other controls, and uses byte-CAS plus atomic rename. It never signals a process or operates on a Unit/cgroup.

## UI observation

`ui_driver.py` has two exclusive modes: `--prepare-only` leaves the dedicated authenticated Run page ready and never clicks; `--execute-reviewed-run` requires both the fresh `HOLD_ARMED` proof and the exact prepared-session proof. The unique agent-browser session auto-launches its own browser with a new 0700 profile directory under `/tmp`; the driver resolves its dynamic loopback CDP URL and matches the listening socket to exactly one browser process, recording PID/startticks/UID/exe SHA plus the profile path/dev/inode/UID. The profile never enters the evidence directory. The reviewed Run phase requires that exact process fingerprint and private profile identity to remain live and never attaches to a shared CDP port. It uses only the real RunTask page and its confirmation button, never the child Run API. On failure or after the reviewed run, it closes only that session and removes the profile only if its path, inode, owner, and mode still match the recorded fixture.

`ui-network-observer.js` observes only the rendered application’s own `/api/me`, exact child Task, and exact Execution requests. It stores only response status and approved identity/status fields; it never stores request headers, tokens, or raw bodies. Once the Execution row link is opened, the driver records the badge from the detail page’s status card, the same-ID API oracle (ExecutionID/TaskID/NodeID/status), badge timestamps and monotonic elapsed values, the nonce-derived stdout marker, and document `timeOrigin`/history/path stability. The success detector reads the status badge rather than matching a generic page toast. If the RUNNING badge is not observed, the result remains partial and the controller never retries the Run.

The prepare failure and execution finalizer clear the dedicated browser’s session storage. Logout is sent with the same locally obtained login session, then `/api/me` is checked using that revoked session and must return 401 before the browser session closes. The role check is the actual `administrator` value used by the application. Login's own failure path also revokes any already-created session before returning an error, including failures before the token can reach the caller. A successful prepare deliberately leaves the one dedicated session open until the reviewed run stage; a failed prepare logs out and closes it.
