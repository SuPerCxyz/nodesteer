## 1. 真实链路与根因

### 1.1 链路（读代码确认，非推测）

1. Hub：`internal/hub/execution.go:66-105 executionEnvironment()` 从 task/script 的 `type=secret` 参数收集明文值 → `payload.SecretValues`（`internal/hub/execution.go:294,312`）。
2. Agent：`internal/agent/agent.go:1623 localSecretValues()` 同样收集本地直跑的值；`executeTask` 在 `internal/agent/agent.go:1082-1118` 建两个**每流一个**的 `streamRedactor`，`runner` 的 `OnLogChunk` 里逐分片脱敏后发 `MsgLogChunk`；执行结束后用 `redact()` 处理终态 `stdout/stderr`（`internal/agent/agent.go:1144-1146`）。
3. 分片来源：`internal/agent/execution/runner.go:293-311 streamWriter.Write()`，单帧上限 `logChunkSize = 64<<10`（证据里的 32KiB 是网关侧落库切分）。
4. Hub 侧**没有**任何二次脱敏：`grep -rn 'REDACTED|redact' internal/hub/` 为空 → 日志脱敏完全依赖 Agent 侧；Hub/UI 只是把 Agent 送来的分片按 seq 拼接展示。

### 1.2 根因

修复前的 `streamRedactor.write()`（原 `internal/agent/redact.go`，57 行）只做两件事：

- **整值匹配**：`strings.HasPrefix(pending, secret)`，即只有"完整 secret 值"连续出现时才输出 `[REDACTED]`；
- **起始前缀保留**：`strings.HasPrefix(secret, pending)`，只对"secret 开头的一段"做保留/收尾遮蔽。

因此：

- 值的**任意连续子片段**（去头段、去尾段、中段）既不等于整值、也不是 secret 的起始前缀 → 按普通字节逐字节原样输出，`redacted` 计数 0；
- 两个流各有独立状态（`redactors["stdout"]/["stderr"]`），跨流两段互不可见；
- 因此证据中三种形态（同分片前后段、跨 stdout/stderr 两段、1MiB 头尾两段）**并集即可还原完整值**，与分片大小无关（这一点与"跨 chunk 重组"的旧口径不同：新证据的拆分发生在**脚本内部**，任何分片策略都挡不住）。

### 1.3 负向对照（修复前算法复跑同样输入，临时 harness 位于 `/tmp/opencode/oldredact`，不入库）

| 变体 | 修复前输出 | 结论 |
|---|---|---|
| 1 同分片前后段 | `QAMARK-HALVES-8970c813-01234567` + `ALVES-8970c813-0123456789abcdef` 两段原样可见 | 两段并集 = 完整值（与证据一致） |
| 2 跨流两段 | stdout 去头段 `ROSS-8970c813-abcdef0123456789` 原样可见；stderr 去尾段因是 secret 起始前缀被遮蔽 | 泄漏 30/38 字符（证据 G8 cross 探针 stderr 的 `-abcdef0123456789` 同样原样可见） |
| 3 1MiB 头尾 | 头段、尾段均原样可见 | 两段拼接可还原完整值（与证据 `reconstruct_note` 一致） |

## 2. 方案与取舍

### 2.1 采用的方案：分片级 + 跨分片状态化 + 跨流尾部联合判定

`internal/agent/redact.go`（整体重写）：

1. **分片索引**（`newSecretIndex`，每个执行构建一次，两流共享只读）：
   - 对每个长度 ≥ `minFragmentLen(8)` 的 secret，取其**全部 8 字节连续子片段**，大端打包成 `uint64`，排序去重（`grams []uint64`）；
   - 额外建 8 KiB 位图 `ends`：预筛"末尾两字节是否可能结束某个分片"，让普通日志上的查找退化为一次数组访问；
   - 长度 < 8 的 secret 走整值匹配（`short []string`）。
2. **逐字节状态机**（`streamRedactor.write`，每流一个实例，调用方串行使用）：
   - 每个位置判断"以该字节结尾的 8 字节窗口是否是某个分片"，命中即进入**遮蔽区间** `run`，区间延续到窗口不再命中为止，整段写一个 `[REDACTED]`；
   - 区间结束时，已遮蔽的尾部（≤7 字节）进入 `look` **回看缓冲**（只参与窗口判定、永不输出），使"片段起点被上一次遮蔽吃掉、后续字节仍属同一片段"的续接也能命中；
   - `safe` 只推进到"**可能是分片起点**"的位置：≥8 字节可用时由窗口判定（结论性），<8 字节可用时用前缀范围查询（`couldStartFragment`，结论性：返回 false 则追加任何后续字节都不可能构成分片）；
   - 因此**普通输出不额外等待**（与修复前一致），只保留"看起来像某个分片开头"的 ≤7 字节尾部与已确认的遮蔽区间。
3. **跨流联合判定**（`finishStreamPair` / `jointTailDanger`）：流结束时把两流保留的尾部（各 ≤7 字节，双向拼接）做一次分片/短值判定，命中则两流尾部一起遮蔽 → 覆盖"两流各留一段、并集才够 8 字节"的形态。
4. **收尾口径**（`finish`）：被切断的遮蔽区间 → 整段遮蔽；保留尾部若是"secret 起始前缀"→ 整段遮蔽（**保持修复前口径**，取消/超时/截断场景不回退）；其余不足阈值的尾部按普通字节写出（不制造误报）。

### 2.2 被否掉的备选与理由

| 备选 | 否决理由 |
|---|---|
| 按行缓冲后脱敏再分片 | 无换行的长输出/二进制输出会无界缓冲或无界延迟；且"行内查找子片段"仍需同一套分片判定 |
| 固定保留尾部窗口（永远扣住最后 7 字节） | 能覆盖分片，但会让**每次 write 的最后 7 字节**在实时日志里延迟到下一次输出（安静进程最后一行显示不全），且收尾时对普通尾部还要额外定义误报策略 |
| 只对终态字段做拼接后脱敏 | 实时 `MsgLogChunk` 已经发出，Hub/UI 按 seq 拼接即为证据里的泄漏路径 |
| 对 secret 长度设人为上限 | 见 §4，索引本身 O(8×Secret 字节数)，不需要上限；超长值由遮蔽区间机制天然覆盖 |

### 2.3 阈值 K=8 的理由（`internal/agent/redact.go:19`）

- 三个证据形态产生的片段长度都 ≥ 19 字节，K=8 覆盖并留有余量；
- K 越小误报越多（会把普通文本里 8 字节以内的巧合子串也遮蔽），K 越大覆盖越弱；
- 低于 K 的片段与普通文本**在原理上不可区分**（见 §6 残余形态），这是阈值型脱敏的固有边界。

## 4. 内存 / 性能上界与理由

| 维度 | 上界 | 理由 |
|---|---|---|
| 分片索引 | ≈ `8 × Σ(len(secret)-7)` 字节 + 8 KiB 位图 | 每个 8 字节分片一个 `uint64`；去重后更小；**每次执行构建一次**，stdout/stderr 与终态字段共享；与日志长度无关 |
| 单流保留 | ≤ `maxRunHold(64 KiB) + 单次分片(≤ logChunkSize 64 KiB) + 7` ≈ 128 KiB | 非遮蔽区间时只保留 ≤7 字节；遮蔽区间达到 64 KiB 立即写出占位符并继续（`internal/agent/redact.go:202-208`） |
| 输出放大 | 每个遮蔽区间一个 `[REDACTED]`（10 字节），区间 ≥ 8 字节时净增 ≤ 2 字节 | 只在真实命中处替换 |
| 单流复杂度 | O(流字节数)（摊还） | 每字节一次窗口判定（预筛命中才二分）+ `safe` 推进（摊还 ≤1 次前缀查询） |
| 超长值（> 保留窗口） | 与长度无关地**完整遮蔽** | 值的每个位置都在遮蔽区间内（区间由窗口判定驱动），> 64 KiB 的值会输出多个 `[REDACTED]`，仍不泄漏 |
| 超长值（> maxRunHold） | 同上，输出多个占位符 | 单测覆盖（>64 KiB 值，见 §5） |
| Secret 长度上限 | 不设人为上限 | Secret 本身已随执行负载常驻内存；索引是它的 8 倍常数倍 |

本机真实基准（`go test -bench`，i5-12400，2 MiB 输入、64 KiB 分片）：

| 场景 | 修复后 | 修复前（临时 harness 复跑同一基准） |
|---|---|---|
| 无 secret | **137 ns/op、0 alloc**（纯直通） | 7.69 ms/op、9.1 MB alloc |
| 3 个 secret | **15.5 ms/op ≈ 136 MB/s**、3.7 MB alloc | 28.4 ms/op ≈ 74 MB/s、9.3 MB alloc |

即：无 secret 路径从"逐字节重建字符串"变成零拷贝直通；有 secret 路径比修复前快约 1.75×。

## 6. 残余形态（Agent 侧无法完全覆盖）与两侧配合最小方案

### 6.1 残余形态

1. **< 8 字节的片段**：把值切成任意多个 <8 字节片段（例如对 12 字节口令用 `cut -c1-4`/`cut -c5-8` 分两次打印），每段都与普通文本无法区分 → 不遮蔽，并集仍可还原。这是阈值型脱敏的固有边界（阈值取 4 会显著增加普通日志误报）。
2. **跨流的短片段且不可延展**：两段各自 <8 字节、且都不是"可延展的分片前缀"（典型是值的末尾若干字节，例如 `tail -c4`），并且不在流末尾（流末尾已由 `jointTailDanger` 覆盖）→ 可重组。
3. **低熵 Secret 的"接缝"残余（已复现并量化）**：当 Secret 字母表极小（如 `abbaaaabbb` 这种 2 字母重复串）、且脚本把两个分片**相邻拼接**打印时，遮蔽区间可能在第二个分片内部因"跨接缝的 8 字节窗口恰好命中"而提前中断，第二个分片尾部会被当作普通字节写出。实测口径：
   - 泄漏量恒 **< 8 字节**（`TestStreamRedactorRepetitiveSecretResidual` 对 chunk=1/2/3/7/8/16 断言 `len(泄漏) < minFragmentLen`，且输出中不存在任何 ≥8 字节分片）；
   - 需要**接缝处巧合命中**才会触发：随机属性测试（26 字母表、20000 次随机 Secret/片段/分片大小，含相邻分片）**未出现**该形态（`TestStreamRedactorRandomizedFragments`）；
   - 攻击者用 <8 字节片段本就能达到同样效果（§6.1-1），因此该形态**不增加新的泄漏能力**，只是"≥8 字节连续分片必然整体遮蔽"这一更强性质在低熵输入下的例外。
   - 彻底闭合需要在 Agent 侧引入"最长可续接匹配长度"状态机（等价于对全部分片建 AC 自动机/后缀自动机），代价是每个字节多次前缀范围查询与更大的索引内存；本轮按"不增加新泄漏能力、保持内存与性能上界"取舍，未实现。
4. **脚本可任意变换值**：secret 会注入 `NODESTEER_PARAM_*` 环境变量（`internal/agent/agent.go:1620-1621`），脚本可以 base64/逐字符/加噪输出，任何脱敏都挡不住。脱敏只防**意外**泄漏，不是对抗恶意脚本的边界。

### 6.2 两侧配合最小方案（本次**未实现**，仅给方案；超出本轮授权范围）

1. **Hub 侧读取时复用同一分片规则**：Hub 已持有 task 的 secret 值（`executionEnvironment`），在 `GET /api/executions/{id}/logs` 与执行详情返回前，对**组装后的** stdout/stderr 做一次分片脱敏（同一 K=8 与同一"并集"判定，可含跨流尾部判定）。这样能覆盖：旧版本 Agent 送来的历史/实时数据、以及 §6.1-2 的跨流短片段在 Hub 侧的并集重组；只改读取路径，不改存储、不改协议。
2. **产品侧最小长度**：secret 参数建议最小长度（如 ≥16 字符）或在保存时对短 secret 告警，使"去头 8/去尾 8"这类拆分无法产生 <8 字节片段。
3. **文档/UI 口径**：明确"secret 以环境变量注入、脚本可读取"，脱敏是纵深防御而非唯一控制。

## 7. 对外可见行为变化（逐条）

1. **拆分片段被遮蔽**：三种拆片形态下，日志里出现 `[REDACTED]`（此前原样可见、`redacted` 计数 0）；两段并集不再能还原完整值。
2. **遮蔽粒度**：一个连续片段写一个占位符；跨 chunk 边界会合并（不再因分片边界把一段拆成多个占位符）。
3. **跨流**：stdout/stderr 各自的分片各自遮蔽；两流收尾保留尾部会做一次联合判定，命中时两流尾部一起遮蔽。
4. **终态字段与实时分片使用同一判定**（`redactStreams`），包括跨流判定，二者语义一致。
5. **普通输出不额外缓冲**：与修复前一致，只有"尾部看起来像某个 Secret 的起始片段（≤7 字节）"时保留到下一分片/收尾；该尾部若不是 secret 起始前缀，收尾按原样写出（不会误报 `[REDACTED]`）。安静进程的最后 ≤7 字节可能延迟到下次输出（与修复前"保留 secret 起始前缀"同类，触发面略宽）。
6. **收尾遮蔽口径保持**：被取消/超时/截断切断的 secret 起始前缀仍整体遮蔽（`isSecretPrefix`），`TestSecretTerminalJournalBoundaries` 的 timeout/cancel/truncated 期望不变。
7. **既有测试期望变化（属修复语义，不是回归）**：
   - `split-streams`：stderr 由"原样 suffix"改为 `[REDACTED]`；
   - `retry`：第二次尝试的 stdout 由"原样 suffix"改为 `[REDACTED]`。
8. **性能/内存**：无 secret 直通 0 分配（此前每字节重建字符串）；有 secret 2 MiB 日志 16.2 ms（此前 28.4 ms）；新增约 8×Secret 字节数的索引（每执行一次，两流共享）+ 8 KiB 预筛位图，单流保留 ≤ ~128 KiB。
9. **新增回看缓冲**：遮蔽区间结束时，已遮蔽的尾部（≤7 字节）保留在内存中只用于窗口续接判定，永不输出（内存影响可忽略，见 §4）。
10. **未改**：Hub 存储/API 契约、协议字段、Web/UI、`.e2e/**`。

## 9. 未验证项、限制与建议

- **未在真实 Hub/Agent 环境复测 X16**（本机只做到：单测 + 真实 `runner`/journal 链路 + 负向对照）。建议 E2E 批次用 G8 的同一脚本夹具与新二进制复测，预期：三个形态均出现 `[REDACTED]`、`redacted` 计数 ≥ 1、两段并集不可还原。
- **Hub 侧改动未做**（§6.2 方案），历史数据与"两流短片段并集"仍需 Hub 侧读取时兜底才能覆盖。
- **阈值以下片段（<8 字节）不遮蔽**，属设计选择，已在 §6.1 如实列出；如需更严，需要产品侧裁决（会显著增加普通日志误报或要求 secret 最小长度）。
- **低熵 Secret 的"接缝"残余（§6.1-3）未闭合**：泄漏量恒 <8 字节、不增加新泄漏能力，但"≥8 字节连续分片必然整体遮蔽"这一更强性质在低熵输入下不成立。闭合需要在 Agent 侧引入最长可续接匹配状态机（AC/后缀自动机），会带来每字节多次前缀查询与更大的索引内存；如产品要求该更强性质，建议单独开一个 change 评估（或按 §6.2-1 在 Hub 读取侧兜底）。
- 未改 `.e2e/**` 状态文件、`docs/**`、`openspec/**`；未做 Git 操作；未装依赖。
