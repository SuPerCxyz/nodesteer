## 一、方案选择与理由

**选择方案 A：给四类行明确终态**（复用既有终态机制 `phase=DONE` + `completed_kind`），未采用方案 B（只读查询面）。理由：

1. **直击根因**：CR-3 的两个症状是“行永久留在活动部署集合”和“每次重启重复告警”。终态化同时消除两者；只读查询面只能“看见”，活动集合仍无限增长、告警仍重复。
2. **零新 phase、零渲染风险**：新增 phase 值需要同步 `GetActiveDeployments` 过滤、UI/审计渲染与文档 Phase 枚举。复用 `DONE + completed_kind` 后，`GetActiveDeployments`（`phase NOT IN ('DONE')`）自动收敛活动集合，`completed_kind` 本就是“DONE 的终态成因”字段（既有 `prepare_failed`/`rolled_back` 同样是“非成功 DONE”），语义一致。
3. **安全语义不变**：四类行仍在任何回滚动作之前 `continue`，不重放；新终态成因均不等于 `deployed`，不会被 `supersededByLaterDoneDeployment` 当作取代依据（新增单测固化）。
4. **运维出口**：方案 A 自带出口（恢复即自动标记，无需人工清理）；同时按评审建议补了**启动汇总日志**（关闭行按成因计数、仍活动行列 ID），弥补“静默悬挂”。

全仓核查确认部署 journal 只被 `RecoverDeployments` 消费（`GetActiveDeployments` 唯一调用点；`ListAllDeployments` 无调用方；Hub/前端/审计不消费 Agent 本地 journal），因此新增 `completed_kind` 取值不产生渲染/兼容问题。

**四类行 → 终态成因映射**

| 行类别 | 判定条件 | 终态 `completed_kind` | 语义 |
|---|---|---|---|
| superseded | 同应用存在更晚的 `DONE + deployed` | `superseded` | 陈旧 backup 不得覆盖更晚成功部署，无需人工动作 |
| 绑定漂移 | 绑定字段齐全但与当前定义不一致 | `stale_binding` | backup 归属未知，需人工判断 |
| legacy 缺绑定 | `app_revision`/三路径任一为空（升级前写入） | `legacy_unbound` | 归属未知，需人工判断 |
| PREPARING | 恢复时 `phase=PREPARING` | `prepare_interrupted` | 未产生宿主副作用，文件保留、不重放 |

新增助手：

```go
// closeUnreplayable 把恢复阶段判定为不可重放的 journal 行落终态（DONE + completed_kind），
// 使其离开活动部署集合、重启不再重复告警；终态成因均不等于 deployed，不会构成取代依据。
// 返回 false 表示写入失败，行保持活动，下次启动重试。
func (am *ApplicationManager) closeUnreplayable(ctx context.Context, d *DeploymentRow, kind, detail string) bool {
	if err := am.store.CompleteDeployment(ctx, d.ID, kind, d.BackupPath); err != nil {
		am.logger.Error("close unreplayable deployment journal failed", "id", d.ID, "app", d.ApplicationID, "kind", kind, "error", err)
		return false
	}
	am.logger.Error("unreplayable deployment journal closed", "id", d.ID, "app", d.ApplicationID, "kind", kind, "detail", detail)
	return true
}
```

## 三、对外可见行为变化（逐条）

1. **四类不可重放行在恢复时落终态**：`phase=DONE` 且 `completed_kind ∈ {superseded, stale_binding, legacy_unbound, prepare_interrupted}`，不再出现在活动部署集合，Agent 重启不再重复告警（原为永久悬挂）。
2. **journal 新增 4 个 `completed_kind` 取值**（原 3 个）。**未新增 phase 值**，无 UI/审计渲染变化（journal 无 Hub/前端消费方）。
3. **PREPARING 行的“唤醒已登记旧服务”只在首次恢复尝试一次**（原来每次重启都重试）。若唤醒失败仍记错误日志，但不再自动重试；服务可通过 systemd 正常手段恢复。
4. **新增两条恢复汇总日志（Warn）**：
   - `unreplayable deployment journals closed by recovery`（`closed="superseded=1,stale_binding=1,…"`）
   - `deployment journals still active after recovery`（`ids=…,count=N`；覆盖无法判定、回滚重放失败、终态写入失败的行）
5. **绑定漂移改为一次性判定**：首次恢复观察到漂移即关闭为 `stale_binding`；此后即使应用定义回退，也不再重放该行（原为每次重启重新判定、理论上定义回退后仍可重放）。与既有“未知→不重放”的已确认取舍一致。
6. **不变项**：陈旧 backup 一律不重放；`ROLLBACK_FAILED`/`ROLLING_BACK` 在绑定匹配且无更晚成功部署时仍可重放收敛（`TestRollbackFailureMarksRollbackFailedPhase` 等原用例保持通过）；准备阶段不触碰宿主文件；回滚重放的双重防护与顺序不变。

## 五、未验证项与剩余风险

1. **运行时验证缺口**：本报告为静态 + 单测层证据；“升级后首次重启关闭历史行、第二次重启无告警”的实机演练未执行（需真实 Agent 数据目录与重启）。单测已用真实 SQLite + 注入日志覆盖等价路径。
2. **`stale_binding` 的一次性语义**（行为变化 5）：定义漂移行关闭后不可逆；若后续产品要求“定义回退后可重放”，需增加显式重开入口。
3. **PREPARING 唤醒不重试**（行为变化 3）：若首次唤醒失败且无人干预，服务保持未启动；错误日志与汇总行可见，但无自动重试。
4. **运维随时可查性**：终态行的持续可见性依赖 journal 记录本身（`completed_kind`）；仓库现状无部署 journal 的 CLI/API（`ListAllDeployments` 无调用方）。若要求“随时列出待人工处理行”，需新增只读查询面（本次未纳入）。
5. **`应用定义缺失` / `恢复单元非法` / supersession 查询失败** 三类行仍保持活动（可能随定义重新同步而可恢复），只进“仍活动”汇总，不做终态化——不在 CR-3 四类范围内。
